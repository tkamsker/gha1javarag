This first-phase PRD defines a Python CLI pipeline that scans Java-family source trees, uses a local Ollama model (`gemma3:12b`) to understand each file, and indexes structured artifacts plus embeddings into a local Weaviate instance for later PRD and requirements generation.[1][2]

## Scope and Objectives

- Build a Python application with a Click-based CLI that operates in phases: discover, extract, and index; later phases (search, PRD generation, requirements generation) are out of scope for this iteration but must be anticipated in the data model.[3]
- Ingest complete legacy Java/JSP/GWT codebases, treating each `pom.xml` root as a distinct project and capturing module hierarchy, file-level artifacts, and LLM-generated summaries into Weaviate for semantic search and downstream PRD creation.[1]
- Use a local Ollama-hosted `gemma3:12b` model as the single LLM provider for file understanding, classification, tagging, and summarization; all interactions must work against `localhost:11434` using the Ollama HTTP API.[2][4]

## Environment and Configuration

- The pipeline reads configuration from a `.env` file, with at minimum: `JAVA_SOURCE_DIR` (root path for code discovery), `WEAVIATE_URL` (e.g., `http://localhost:8080`), `OLLAMA_MODEL_NAME` (default `gemma3:12b`), and optional flags such as `MAX_TOKENS`, `CHUNK_SIZE`, and `DRY_RUN`.[2][3]
- Weaviate runs in a local Docker container (or docker-compose stack), with the Python client configured to use the provided URL and optional API key; the application must validate Weaviate availability and schema on startup.[3][1]
- The CLI must be idempotent: re-running on the same codebase should either upsert documents (based on a deterministic key like `project_id + file_path + hash`) or provide a `--reset-project` flag to clear prior data for the identified project(s).[1]

## CLI Architecture and Subcommands

- Implement a top-level `codeindex` CLI (name can be refined) using Click, with subcommands: `discover`, `extract`, `index`, `search` (basic), and `status`; for this phase, `discover`, `extract`, and `index` must be fully implemented, while `search` and `status` can be minimal but functional.[5][3]
- `codeindex discover`: recursively walks `JAVA_SOURCE_DIR`, recognizes project roots where `pom.xml` exists, and emits a structured inventory (JSON or SQLite/JSONL) of projects, modules, and files, including file type classification based on extension and heuristics (e.g., `.java`, `.xml`, `.jsp`, `.js`, `.html`, `.sql`, `.properties`).  
- `codeindex extract`: reads the discovery inventory and performs static extraction per file to capture structural and contextual metadata, and calls the LLM to generate per-file semantic summaries and tags; outputs a normalized artifact representation ready for indexing.

## Project and Module Detection

- Any directory containing a `pom.xml` is considered a Maven project; the tool must assign a stable `project_id` (e.g., from Maven `groupId:artifactId:version` when available, or a hash of path plus POM contents as a fallback).[1]
- The extractor must parse each `pom.xml` to capture at least: `groupId`, `artifactId`, `version`, `packaging`, module declarations (`<modules>`), plugin usage, dependency coordinates, and Maven profiles relevant for understanding the build and module relationships.[1]
- The directory tree under each project root must record: `source_roots` (e.g., `src/main/java`, `src/main/resources`, `src/main/webapp`), test sources, and any `gwt.xml`, iBATIS/MyBatis mapping files, or other framework-specific config files discovered during the scan.

## File Classification and Artifact Types

- The system must classify files into semantic types including, but not limited to: `java_source`, `java_test`, `jsp_view`, `html_template`, `gwt_module`, `js_script`, `sql_schema`, `sql_query`, `orm_mapping`, `ibatis_mapping`, `xml_config`, `properties_file`, `static_asset` (css/images), and `other_text`.  
- Classification initially uses file extensions and path patterns, then the LLM validates or refines the classification using short prompts on representative content (e.g., first N lines or chunks) to distinguish between similar XML types like Spring config vs. Hibernate mapping vs. GWT descriptor.  
- Each artifact type must map to a consistent set of attributes in the internal model, such as `java_source` with package, imports, class/interface names, methods, and annotations; `jsp_view` with form actions, taglibs, and referenced controllers; and `sql_schema` with table, column, and constraint definitions.

## LLM Integration and Responsibilities

- The app uses Ollama’s HTTP API for generating structured JSON responses from `gemma3:12b` given prompts that: classify the file, summarize its purpose, extract key entities (classes, functions, forms, endpoints, queries), and propose meta tags relevant for indexing and PRD generation.[4][2]
- Prompts must be deterministic, concise, and ask explicitly for machine-readable output (e.g., JSON with fields `summary`, `roles`, `entities`, `tags`, `language`, `frameworks`, `concerns`, `dependencies`), with basic validation/parsing and fallback behavior when output is malformed.  
- The LLM must be aware of code language and context: prompts should include hints like “This file is likely Java/JSP/GWT/XML/SQL” along with the extension and relative path, and should instruct the model not to hallucinate missing code and to signal uncertainty with confidence scores.

## Weaviate Schema Design

- Define a Weaviate schema that supports at least two primary classes: `Project` and `CodeArtifact`, where `Project` holds POM and module-level metadata and `CodeArtifact` holds one file/chunk plus LLM-derived understanding; both must be configured with vectorization for semantic search.[3][1]
- `Project` properties include: `projectId`, `name`, `groupId`, `artifactId`, `version`, `packaging`, `path`, `modules`, `dependencies`, `frameworks`, and an optional `summary` generated by aggregating project-level information (can be added in a later phase but reserved in schema).  
- `CodeArtifact` properties include: `projectId`, `relativePath`, `fileName`, `language`, `artifactType`, `frameworks`, `summary`, `entities`, `tags`, `dependencies`, `pomContext` (e.g., Maven coordinates), `chunkIndex` (if chunked), and `rawTextHash`; the vectorization uses the `summary + tags + entities + selected code context` as the text to embed.

## Embeddings and Chunking Strategy

- For large files, the extractor must chunk code into logical units (e.g., classes, methods, or sections separated by markers), targeting a maximum token length compatible with `gemma3:12b` and the chosen embedding approach; chunks must preserve ordering via `chunkIndex` and `chunkCount` fields.  
- Embeddings can be produced either by Weaviate’s internal vectorizer (if configured) or via an external embedding path; for this phase, the requirement is to use Weaviate’s configured vectorization and provide a consistent `text` input per artifact or chunk, avoiding direct embedding calls from Python unless necessary.[6][1]
- Each chunk or artifact record must keep both the human-readable `summary` and the original code snippet or a reference to its location, enabling reconstruction of context for RAG and PRD generation in later phases.

## Metadata and Tagging Requirements

- The LLM must generate a normalized `tags` set capturing at least: `layer` (backend, frontend, integration, persistence, config), `domain` (auth, billing, reporting, etc.), `frameworks` (GWT, Struts, Spring MVC, iBATIS/MyBatis, JDBC, JSP, Servlet), `technology` (Java, SQL, HTML, XML), and `concerns` (security, validation, business_rule, data_access, UI_flow).  
- The extractor must also add deterministic tags based on directory path and file type, such as `test`, `config`, `resource`, `view`, or `controller`, so that search is not solely reliant on LLM output.  
- All tags and metadata must be stored in Weaviate as arrays of strings or appropriate types, enabling filter-based queries alongside vector search (e.g., “find all jsp_view artifacts in project X related to authentication”).

## Error Handling, Logging, and Observability

- The application must implement robust error handling: transient Weaviate or Ollama failures should trigger retries with exponential backoff and clear logging; persistent failures should be recorded and surfaced at the end of execution in a summary.[2][1]
- Logging should be structured and configurable (e.g., log level via env/CLI), recording key events: project detection, file counts per type, LLM calls, indexing success/failure per artifact, and performance metrics (e.g., time per phase, time per LLM call).  
- A `status` or `report` command must provide a quick overview of indexed projects and artifacts from Weaviate, including counts per project and artifact type, so that users can validate ingestion completeness during this first phase.

## Non-Functional Requirements

- The initial implementation must be single-node and suitable for running on a developer workstation with limited memory; the system should process large codebases incrementally and support resuming from partial runs (e.g., skip already hashed/indexed files unless `--force` is set).  
- The design must be friendly to Spec Kit and PRD-based workflows: data structures, naming, and CLI behavior should be simple and explicit so that Spec Kit-driven agents (Claude, Cursor) can generate and maintain the implementation with minimal ambiguity.[7][5]
- Intellectual property must be respected: only locally stored source code is processed, no external calls to cloud LLMs are allowed in this phase, and no code is transmitted outside the local environment except to the local Ollama and Weaviate instances.
